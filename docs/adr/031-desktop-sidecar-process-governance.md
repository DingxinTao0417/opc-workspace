# ADR-031：桌面受管 Sidecar 的进程树治理（Windows Job Object）

- 状态：Accepted（2026-10-04）
- 决策范围：桌面壳对内置 Sidecar 及其后代进程的回收；属于 v0.1 桌面基座（PRD T-02），不改变版本边界
- 相关文档：[桌面与平台模块](../modules/desktop-platform.md)、[ADR-027](027-builtin-agent-executor-and-run-lifecycle.md)、[ADR-003](003-local-agent-runtime-security.md)

## 背景

桌面壳通过 shell 插件启动内置 Sidecar，并约定“父控制管道关闭即优雅退出”。这个约定依赖 Sidecar 自己还在运行：

- 桌面进程崩溃或被结束时，发行构建不会执行退出钩子，只能等 Sidecar 读到管道关闭后自行退出。Sidecar 一旦卡死，就不会响应。
- 卡死的 Sidecar 继续占有数据库运行锁。下一次启动的新 Sidecar 立即退出，两次重试后停在错误页，用户只能自己去任务管理器结束进程。
- Sidecar 启动的 Agent 执行器由 Sidecar 持有的 Job Object 回收。Sidecar 卡死但没有退出时，执行器也一直活着。
- 桌面的强制终止只结束 Sidecar 这一个进程。

此前文档把这一状态记为“没有 Job Object、进程组或孙进程治理，卡死的孤儿只会被运行锁挡住，不会被回收”。

## 决策

### 1. 每一代 Sidecar 一个桌面持有的 Job

- 桌面为每一代 Sidecar 创建一个匿名、句柄不可继承、只设置 `KILL_ON_JOB_CLOSE` 的 Job Object，并把 Sidecar 进程放进去。句柄由桌面进程持有，不设置内存或其他限制，不开启 breakaway。
- 桌面进程以任何方式结束时，操作系统关闭这个句柄，Job 内的全部进程随之终止。不按进程名匹配。
- 一代一个 Job，不复用。上一代意外退出后，它的 Job 随控制对象一起关闭，残留的后代在下一代启动前被清掉。

### 2. Job 放在控制对象内部

Job 是 Sidecar 控制对象的一部分，而不是与它并列的字段。关闭流程会先把控制对象从管理器里取出，再写入优雅关闭请求；并列存放的 Job 会在取出时被丢弃，Sidecar 还没收到请求就被终止。放在内部后，Job 只在三种情况下关闭：已确认退出、强制终止、桌面进程死亡。

### 3. 挂载时机与竞态

挂载发生在登记这一代的同一把锁内，紧跟在启动调用返回之后。启动返回到挂载完成之间有极短的窗口，但 Sidecar 在拿到运行锁、完成恢复并打开数据库之前不会启动任何子进程；即使有执行器在窗口内启动，它也在 Sidecar 自己持有的 kill-on-close Job 里，结束 Sidecar 即回收。因此不为消除这个窗口而绕过 shell 插件自行以挂起方式创建进程。

### 4. 强制终止覆盖整棵树

优雅关闭的顺序不变：写入关闭请求，等待，超时后强制终止，再等待真实退出确认。强制终止改为终止整个 Job，失败时回退到只终止 Sidecar 进程。退出码与原来一致，仍然只有真实的进程退出事件才算退出。

### 5. 挂载失败时失败关闭

Job 创建、配置或挂载失败，且进程仍在运行时，桌面不让这一代 Sidecar 继续运行：照常登记这一代，立即走既有的强制停止流程，等真实退出后按既有预算重试，两次后进入错误页。这与手动终端和 Agent 执行器的做法一致。进程在挂载前已经自行退出不算治理失败，按普通退出处理。

### 6. 与执行器 Job 的关系

Sidecar 启动的执行器自动属于桌面的 Job；Sidecar 再把它放进自己新建的 Job 时形成嵌套（Windows 8 及以上支持）。执行器 Job 的 1 GiB 内存上限和“只回收该执行器子树”的语义不变。

## 后果

- 桌面崩溃或被结束后不再残留 Sidecar 和执行器，下次启动不会因运行锁失败。
- **桌面进程死亡时，健康的 Sidecar 也会被立即终止**，不再有机会做优雅收尾：没有 HTTP 排空，也没有 WAL checkpoint；正在进行的恢复或迁移会被打断，依赖既有的事务、journal 和启动对账来恢复。这是本决策带来的最大行为变化。正常退出不受影响，仍然先走优雅关闭。
- Sidecar 今后若需要启动应当在桌面退出后继续存活的进程，会被一并终止；届时需要重新评估。
- 卡在不可中断内核 I/O 中的进程仍然可能结束不了，数据库运行锁继续兜底。
- 桌面日志新增两个不含进程号和路径的事件：`sidecar_job_attached`、`sidecar_job_unavailable`。
- 没有 API、schema、设置或界面变化。

## 不做

- macOS 与 Linux 不做进程树治理：shell 插件不暴露进程组或 pre-exec 设置，进程组本身也没有“父进程死亡即终止”的语义；这两个平台尚未构建，也没有就绪的执行器或终端。它们继续只依赖管道关闭后的优雅退出和运行锁。首次构建这两个平台时，首选方案是让 Sidecar 在管道关闭后设置硬期限自行退出。
- 不做运行期健康看门狗；不处理启动前恢复使用的一次性辅助进程。

## 验证

- 确定性测试（Windows，默认门禁）：真实进程树在 Job 关闭后子进程与孙进程都退出；终止 Job 后退出码为 1；对已退出的进程挂载返回“已退出”；优雅关闭请求先到达进程、进程以 0 退出而不是被 Job 提前终止；控制对象被丢弃时卡死的进程树被回收；治理失败时恰好发出一次终止、不伪造退出、真实退出前不启动新一代。Sidecar 侧另有测试证明执行器 Job 在外层 kill-on-close Job 内仍能正常完成和超时回收。
