# ADR-032：业务数据导入的旧版本升级与冲突策略

- 状态：Accepted（2026-10-04）
- 决策范围：业务 JSON 与含文件 ZIP 导入在“源包来自旧 schema”和“非空目标存在键冲突”两种情况下的行为；属于 v0.3“可配置备份与高级导入”，不升 app 或 API 版本，不新增迁移
- 相关文档：[数据管理模块](../modules/data-management.md)、[设置模块](../modules/settings.md)

## 背景

导入此前只在两种情况下可以应用：源与目标 schema 相同且目标为空；或 schema 相同、目标非空但没有任何主键重叠。其余情况一律拒绝。实际核对发现四个问题：

1. **已发布版本的包导不进来。** 仓库已发布的版本停在 schema 51，而“兼容图”只接受 schema 49 和 63–78 的源包。
2. **兼容图内的旧包其实也会被拒。** 兼容图只决定源包应声明哪一份排除表清单，不做任何行列转换，并要求包内的表和列与当前库完全一致。schema 71 给可导出的 `actors` 表加了 `agent_adapter_id` 列，所以真实的 49、63–70 包都会因列不一致被拒。用真实迁移器逐版本比对确认：schema 49 到 79 之间，34 张可导出表只发生过这一次变化。
3. **界面应用不了任何跨 schema 的包。** 前端把“可应用且源、目标 schema 不同”的预检结果当作无效响应。
4. **冲突预检不完整。** 预检只比对主键。唯一索引上的冲突（标签名、发票号、保存视图名、单一活动头像等）要到写入时才暴露，那时回滚备份已经创建；设置行和代码所有的身份（内置 Adapter 预设及其 Agent Actor）在两个工作区里键必然相同，使“追加到已有工作区”在目标保存过设置之后总是被拒。

## 决策

统一流程：**先把源包转换到当前结构，再做现有的严格校验，再对冲突分类，最后按预检给出并经用户确认的方案应用。** 回滚备份、单事务写入和写入后的完整性复验不变。分四片交付，每片独立可用。

### S0 旧版本升级转换

- 受支持的源 schema：49、51、63–78，以及当前 schema。50、52–62 和 49 之前的版本没有可核对的冻结清单，继续拒绝；比当前新的版本继续拒绝。
- 每个受支持的源 schema 对应一份冻结的排除表清单；schema 51 的清单按已发布版本补入。
- 可导出结构的每一次变化登记为一个转换步骤。步骤是作用于内存中包数据的纯函数，前置条件不满足即拒绝。目前只有一步：schema 71 在 `actors` 末尾补 `agent_adapter_id = NULL`；源包若已含 `type = 'agent'` 的 Actor 则拒绝（该类型在 71 之前不可能存在）。
- 一条用真实迁移器逐版本建库的测试守住登记表：可导出表的列在相邻版本间有任何变化而没有登记步骤，测试失败。另有等价性测试：旧库导出再转换的结果，必须等于把该库迁移到当前版本后再导出的结果。
- 仓库保存了两份由 v0.1.0 标签原样构建的 Sidecar 自己写出的导出包（业务 JSON，以及含一个受控文件的 ZIP）作为冻结夹具。上面两条测试用当前代码读取历史库，无法证明真实包的信封、排除清单和 ZIP 布局被当前版本接受；这两份夹具证明了这一点。
- 预检返回 `upgrade_steps`（可以为空数组，表示结构未变）。**源 schema 低于目标时一律使用独立确认词**：`upgrade-and-replace-empty-workspace`、`upgrade-and-append-to-existing-workspace`，ZIP 另加 `-with-controlled-files` 后缀。跨 schema 使用原确认词返回 428，此时不创建备份。
- ZIP 先按原始内容校验哈希，再做内存转换。所有拒绝都发生在创建备份之前。

### S1 唯一语义冲突的只读预检

- 预检对可导出表上的每一个非主键唯一索引（含部分索引和表达式索引）计算“写入后会违反唯一性”的行数：把待导入的行放入临时表，用索引自己的键表达式和条件分别求出两侧的键，主键不同而键相同即为冲突。不逐个手写规则，新增唯一索引自动纳入。
- 预检返回 `semantic_conflicts` 和按表、索引列出的 `semantic_conflict_rules`。存在未被 S2 化解的语义冲突时，阻断原因为 `target_semantic_conflicts`，应用返回 409 `IMPORT_TARGET_SEMANTIC_CONFLICT`。
- 界面把用户认得出的唯一值显示为文字（标签名称、发票号、保存视图名称），其余规则显示索引名。这三个索引名由一条后端测试固定，改名会在那里被发现。
- 这一片只读，不改变任何可应用的情形，只把原本会在写入阶段失败的导入提前到备份之前拒绝。

### S2 保留目标（keep_target）

只对一个封闭集合生效，集合内的行在两个工作区里键必然相同，不代表用户数据重复：

- **设置与头像**作为一个整体：目标已有任何设置行或活动头像时，保留目标的全部设置与头像，不导入源包的 `app_settings`、`workspace_avatars` 及其事件，ZIP 不发布对应的头像文件。目标两者皆无时照常导入。
- **代码所有的 Agent 身份**：ID 固定的内置 Adapter 预设及其绑定的 Agent Actor，在目标已存在时保留目标行，不导入源行及其专属事件。

预检在 `resolutions` 中逐表给出规则和行数。只要存在任何 resolution，预检就返回 `plan_digest`，应用必须带 `X-Import-Plan-Digest`；在维护锁内重算的方案与之不一致时返回 409 `IMPORT_PLAN_CHANGED`，不创建备份。

### S3 跳过完全相同的行（skip_identical）

- 主键重叠且整行逐列相同的行视为已导入，跳过；任何一列不同仍然是冲突，继续阻断。ZIP 中 ID、路径、大小和 SHA-256 都相同的文件同样视为已存在。
- 过滤后的包必须重新通过全部既有校验（自动化关系、收件箱来源历史、Task 产出回放、分派历史），否则按冲突阻断。
- 事务结束前复验被跳过的目标行没有被触发器改动，否则整批回滚。
- **导入必须把行原样放回去，跳过才成立。** 插入子行会抬高所属行的版本：Task、笔记、附件、发票抬高 Project；Project、活动、附件、联系人关联、回访抬高 Client；子任务抬高父 Task。此前只复原了 Project，Client 与父 Task 导入后的 `version / updated_at` 与导出值不同，同一个包再次导入时它们就成了“有分歧的行”。现在三者都在子行写完后复原为导出值，往返测试要求导入后的行与导出的行逐列相同。
- 结果是同一个导出包可以重复导入：用户数据不会重复，全部记为跳过或保留。内置 Actor 与未修改的默认自动化仍按原有规则处理（保留目标 owner、对未修改的预设做幂等合并），因此第二次的 `imported_rows` 不为零。

### S5 应用前演练

- 预检在得出“可以应用”之后，把同一份方案用同一段写入代码在一个**始终回滚**的事务里完整执行一遍：写入全部行、触发全部触发器、做外键检查与一致性复验，然后回滚。它不发布文件，也不创建备份。
- 演练失败时预检返回阻断原因 `apply_rehearsal_failed` 和 `rehearsal_failure.code`，不再给出应用模式与方案摘要。`code` 只是拒绝写入的那条规则的稳定标识：触发器抛出的常量（例如 `TASK_DUE_INBOX_SOURCE_NOT_CURRENT`），或 `UNIQUE_CONSTRAINT`、`FOREIGN_KEY_CONSTRAINT`、`CHECK_CONSTRAINT`、`NOT_NULL_CONSTRAINT`、`INTEGRITY_VALIDATION` 之一。不返回行内容和数据库的原始报错。
- 应用请求在维护锁内重新预检，因此同样先演练：会被数据库规则拒绝的导入返回 422 `IMPORT_REHEARSAL_FAILED`，**不创建回滚备份**。此前这类导入要到备份创建之后才失败（`IMPORT_APPLY_FAILED`），每次尝试都留下一个备份。
- 演练无法得出结论（数据库忙、被取消、I/O 错误）时返回 500 `IMPORT_PREFLIGHT_FAILED`，不当作“数据不可导入”。
- 含文件 ZIP 的演练只覆盖数据库部分。文件只在真实导入时发布，发布后的对象校验失败仍走原有的补偿路径（删除已发布的文件，返回 `IMPORT_PACKAGE_APPLY_FAILED`）。
- 代价：预检不再是纯读取，会短暂占用写锁；应用时写入逻辑执行两遍。导入是低频的人工操作，这个代价换来的是“备份之后才失败”对确定性规则不再可能。

### 明确不提供

- **跳过有分歧的行**：这是静默的部分合并，会把描述源版本的历史事件挂到目标的旧行上。
- **覆盖目标行**：等同于多设备合并，数据管理模块明确不负责；工作流事件也被触发器禁止修改和删除。需要整库替换时使用备份恢复。
- **UUID 重映射（作为副本导入）**本次不做。来自不同工作区的 UUID 主键本来就不会相撞，真实的阻断来自上面的 S1 与 S2；重映射只对“同源包导入为副本”有用，且必然撞上发票号和标签名，需要单独决策。

## 已知限制

**带有历史提醒的工作区目前无法导入。** 收件箱里由系统投影的提醒，各有一条插入守卫，只接受“来源此刻仍处于那个状态”的行：

| 来源                             | 守卫所在迁移 | 何时成为历史行                    |
| -------------------------------- | ------------ | --------------------------------- |
| 任务到期 `task_due`              | 025          | Task 之后被完成、取消、改期或删除 |
| 任务阻塞 `task`                  | 024          | Task 之后解除阻塞或被删除         |
| 内容日历 `content_item`          | 038          | 内容之后改变状态或版本            |
| 路线图里程碑 `roadmap_milestone` | 039          | 里程碑之后改变状态或版本          |

导入按最终状态写入行，所以源工作区只要有一条这样的历史提醒，写入就会被守卫拒绝。“任务到期”与“任务阻塞”两种已用真实导出复现；另外两种是按触发器逻辑判断的，没有逐一复现。同 schema 导入与升级导入、JSON 与 ZIP 都受影响；S1 不覆盖它，因为这不是唯一索引冲突。项目完成提醒（schema 050 的导入授权表）和任务产出提醒（重放）不受影响。

S5 之后，这类包在预检阶段就被明确拒绝并指出是哪条规则，不再创建备份；但**它们仍然导不进来**。真正放行需要让上述守卫识别导入中的历史行，即把 schema 050 的导入授权表推广到这四种来源：一次迁移、四个守卫触发器的重建，以及每种来源各自的历史合法性校验。这超出本决策，需另行立项。

## 后果

- API v1 只增加字段、确认词、阻断原因和错误码；前端对预检结果是闭集解析，前后端必须同版本发布。
- 没有 schema 变化，没有迁移。
- 预检与应用都先演练：能被数据库规则确定性拒绝的导入在创建备份之前返回 `apply_rehearsal_failed` / `IMPORT_REHEARSAL_FAILED`。`IMPORT_APPLY_FAILED` 只剩演练之后才出现的故障。
- 此前“schema 71–78 的源包用普通确认词可应用”的服务端行为改为要求升级确认词。该路径此前在界面上无法触发。
- 同版本、无冲突的导入除一处外行为不变：导入后 Client 与父 Task 的 `version / updated_at` 等于导出值，不再是导入时刻和被子行抬高后的版本。
- 导入成功后界面会重新挂载（设置重新读取），导入结果改由 UI store 保存并在重新挂载后显示。
