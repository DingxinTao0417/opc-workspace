# ADR-034：历史系统提醒的导入授权（schema 80）

- 状态：Accepted（2026-10-05）
- 决策范围：业务 JSON 与含文件 ZIP 导入对四种系统提醒（任务阻塞、任务到期、内容日历、路线图里程碑）的写入；属于 v0.3 高级导入，不改变版本边界。API v1；schema 79 → 80（迁移 `080_business_import_inbox_source_authorizations.sql`）
- 相关文档：[数据管理模块](../modules/data-management.md)、[收件箱模块](../modules/inbox.md)、[ADR-032](032-business-import-upgrade-and-conflict-strategies.md)

## 背景

收件箱里由系统投影的提醒，各有一条插入守卫，只接受“来源此刻仍处于被投影的状态、并且没有被删除”的行：

| 来源                             | 守卫所在迁移 | 何时不再满足守卫                                               |
| -------------------------------- | ------------ | -------------------------------------------------------------- |
| 任务阻塞 `task`                  | 024          | Task 解除阻塞、被删除，或仍然阻塞但之后被编辑过（版本已前进）  |
| 任务到期 `task_due`              | 025          | Task 被完成、取消、改期或删除                                  |
| 内容日历 `content_item`          | 038          | 内容之后改变状态、排期或版本，或被删除                         |
| 路线图里程碑 `roadmap_milestone` | 039          | 里程碑之后改变状态、目标日期或版本（包括改名、排序），或被删除 |

这条规则对在线投影是对的：系统不应凭空写出“某任务正被阻塞”。但导入按最终状态写入行，一个正常使用过的工作区几乎必然留有这样的提醒——任务阻塞和任务到期的提醒不会随任务状态自动归档；内容与里程碑的提醒在来源变化时被归档，归档后的那一行同样不再满足守卫。只要有一条，整个包就无法导入；同 schema 导入、升级导入、JSON 与 ZIP 都受影响。

[ADR-032](032-business-import-upgrade-and-conflict-strategies.md) 的应用前演练使这类包在创建备份之前就被明确拒绝，但它们仍然导不进来。开发工作区的副本里就有一条来源已删除的任务到期提醒。

项目完成提醒在 schema 050 已经用“导入授权表”解决了同一问题；任务产出提醒靠回放解决。本决策把授权的做法用到上述四种来源。

## 决策

### 1. 一张操作态授权表

迁移 080 新增 `business_import_inbox_source_authorizations`，列与 schema 050 的表相同：`inbox_item_id`（主键）、`source_entity_type`（只允许 `task / task_due / content_item / roadmap_milestone`）、`source_entity_id`、`source_event_key`（唯一）、`payload_json`、`source_deleted_at`。

- 它是操作态：平时为空，只在一次导入事务内有行，不进入业务导出。导出的排除表清单因此多一项。
- 不与 schema 050 的 `business_import_project_completion_authorizations` 合并。合并需要重建第五个守卫并删除一张表，行为没有任何变化。

### 2. 四个插入守卫接受被授权的行

迁移重建四个 `BEFORE INSERT` 守卫，名称与报错常量不变：

- **形状检查**（来源 ID、事件键、payload 各字段）保持原规则，但改为对缺失字段也成立。原先的写法在字段缺失时不报错，靠随后“与来源逐项比对”兜住；被授权的行不做那次比对，所以形状检查必须自己成立。
- **来源未删除的行**：来源处于被投影的状态（原规则），或者“来源存在，并且授权表里有与本行完全相同的一条”。否则沿用原常量：`TASK_BLOCKED_INBOX_SOURCE_NOT_CURRENT`、`TASK_DUE_INBOX_SOURCE_NOT_CURRENT`、`CONTENT_ITEM_INBOX_SOURCE_NOT_FOUND`、`ROADMAP_MILESTONE_INBOX_SOURCE_NOT_FOUND`。
- **来源已删除的行**（`source_deleted_at` 非空）：必须有完全相同的授权、时间可解析，否则是 `INVALID_*_INBOX_SOURCE`；并且来源在目标中不存在，否则是新增的 `TASK_BLOCKED_DELETED_SOURCE_COLLISION`、`TASK_DUE_DELETED_SOURCE_COLLISION`、`CONTENT_ITEM_DELETED_SOURCE_COLLISION`、`ROADMAP_MILESTONE_DELETED_SOURCE_COLLISION`。
- “完全相同”指收件箱 ID、来源类型、来源 ID、事件键、`payload_json` 与 `source_deleted_at` 六项逐一相等。
- 新增的 `AFTER INSERT` 触发器 `trg_inbox_source_import_authorization_consumed` 在行写入后删除对应授权：一条授权只放行一次写入。

没有授权的写入与此前完全一样，在线投影不受影响。来源身份不可变、删除协调等其余触发器没有改动。

### 3. 预检核对包内历史

授权由导入代码写入，所以写入之前必须先证明这条提醒确实是系统投影出来的。预检对包内每一条四种来源的提醒核对：

- 恰好有一条 `source_projected` 事件：由系统 Actor 写入，没有前态，后态恰好是收件箱事件状态的 23 个键，其中身份（kind、来源类型、来源 ID、事件键、payload）与这一行一致，状态为 `open`、结清策略为 `manual`、版本为 1、未标记来源删除。
- 来源未删除：来源行必须在包里。来源被删除之前，它的提醒必须先被处理并标记删除，这是数据库强制的。
- 来源已删除：恰好有一条 `source_deleted` 事件，由 Owner 写入，时间等于行上的 `source_deleted_at`，前后两个状态只相差删除标记与版本，当时提醒已是 `resolved` 或 `dismissed`；来源行不在包里；行的版本不低于该事件之后的版本。提醒之后可以被重新打开，所以行当前的状态不作限制。

任何一条不成立，预检与应用都返回 422 `IMPORT_ROW_INVALID`，发生在演练和回滚备份之前。

有意不核对的内容：

- 标题、摘要与优先级。它们由 payload 没有携带的来源字段生成，之后还可以被编辑。
- “投影当时来源确实处于那个状态”。这需要重放来源的全部事件，四种来源各有一套状态机，成本与收益不成比例。
- 来源是否仍处于被投影的状态。这正是本决策放开的部分。

核对只针对完整的包。非空目标的方案会去掉目标已有的相同行（`skip_identical`），其余跨表校验会对去掉之后的包重跑；这一项不重跑，否则“任务已在目标里、提醒是新增的”这种增量导入会因为任务行不在待写入集合里而被判为不成立。

### 4. 应用时写入并用尽授权

- 写入 `inbox_items` 之前，为待写入的每一条四种来源的提醒写一条授权；每条写入用掉自己的授权。
- 事务开始时两张授权表都必须为空，写完收件箱之后也必须为空，否则整批回滚。
- 对来源仍处于被投影状态的行也写授权。它们本来就能通过守卫，写不写授权，被接受的行完全一样；这样导入代码不必复制四份“是否仍是当前状态”的判断。
- 演练走同一段代码，授权随演练事务一起回滚。

### 5. 兼容与迁移

- 迁移只新增一张空表、重建四个守卫、新增一个触发器，不改任何已有行，不带破坏性标记：已有工作区直接升级，不先生成回滚包。
- 可导出的表和列没有变化，没有新的升级转换步骤。schema 79 成为受支持的旧源（受支持的旧源为 49、51 与 63–79）；schema 78/79 的排除表清单被冻结，不会随当前清单变化。
- 回退：迁移没有数据改写，但旧版 Sidecar 不认识 schema 80。回退需要使用升级前的备份，与其他迁移相同。

### 6. 顺带修正：重新打开的项目完成提醒

schema 050 的包内校验要求“项目已删除的完成提醒”此刻仍是 `resolved` 或 `dismissed`。提醒在项目删除后可以被重新打开，这样的工作区导出后会被判为 `IMPORT_ROW_INVALID`。删除事件已经证明删除当时提醒已处理，这项要求被去掉；数据库侧的守卫本来就不限制状态。

## 已知限制

- **追加导入不会删除目标里的东西。** 包里记录某个来源已被删除，而目标仍持有这个来源（目标是更早一次导出导入出来的），这条提醒写不进去，演练以 `*_DELETED_SOURCE_COLLISION` 拒绝整个包。
- **已完成或已取消、并且指派过负责人的 Task 仍然无法导入。** 这与提醒无关，是验证本决策时发现的另一条既有规则：schema 008 的 `trg_task_assignments_reject_terminal_insert` 拒绝为终态 Task 写入任何指派行，包括已经结束的历史指派；导入只对参与产出回放的 Task 提前写入历史指派。演练以 `TASK_NOT_ASSIGNABLE` 拒绝，不创建备份。含有这类任务的工作区目前仍不能导入，尚未修复。
- 历史核对依赖包里的事件日志完整。事件日志只增不改，正常导出总是完整的；手工删改过事件的包会被拒绝。

## 后果

- 带有历史提醒的工作区可以导入，导入后的提醒与源工作区逐列相同，之后的扫描不会重复投影，带活动提醒的来源仍然不能直接删除。
- schema 版本升到 80；导出的 `excluded_operational_tables` 多一项，schema 78/79 的包按冻结清单校验。
- `apply_rehearsal_failed` 不再因为历史提醒出现。设置页相应去掉了“历史提醒目前还不能导入”的说明，新增“来源已删除但目标仍持有”和“历史指派尚不支持”两类说明。

## 验证

- 数据库：`TestBusinessImportInboxSourceAuthorizationIsExactAndSingleUse` 对四种来源逐一覆盖无授权拒绝、内容不符的授权不放行也不被消费、精确授权只放行一次、被授权但来源不存在仍拒绝、来源已删除的三种情形，以及授权表只接受四种来源；`TestBusinessImportInboxSourceAuthorizationMigrationKeepsExistingReminders` 覆盖从 schema 79 无闸门升级且既有提醒不变。
- 接口：`TestBusinessImportRestoresRemindersWhoseSourcesMovedOn` 用真实命令在源工作区里走完“阻塞后解除、阻塞后改名、到期后改期、逾期后完成、提醒处理后删除任务并重新打开提醒、内容排期后修改与删除、里程碑到期后达成改名与删除”，导出后导入空白工作区并逐表比对，再重复导入一次；另有导入后提醒生命周期、历史不完整的八种变体、历史不成立时备份前拒绝、目标已持有来源时的增量导入、重新打开的项目完成提醒，以及“来源已删除但目标仍持有”的演练拒绝。
- 真实数据：开发工作区数据库的副本（其中有一条来源已删除的任务到期提醒）升级到 schema 80 后导出含文件 ZIP，导入空白工作区成功，各表逐行一致。这是一次性核对，不属于默认门禁。
