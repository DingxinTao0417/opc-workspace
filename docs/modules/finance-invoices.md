# 财务与发票模块

> 目标版本：v0.4。本文描述本地优先的收入/支出账本、财务统计和发票管理，不属于 v0.1。

## 定位与边界

本模块保存用户明确录入或确认的财务事实，并把客户、项目、发票与现金流关联起来。SQLite 是业务事实源，金额统一使用最小货币单位整数；图表、KPI 和右侧概览只能来自真实聚合查询。

首版边界：

- 完全在本机保存和处理数据，不依赖银行、支付平台、税务平台或云端财务服务。
- 可生成本地 PDF、CSV 和待办提醒，但不自动发送发票、邮件、催款消息或任何外部请求。
- `sent`、`viewed`、`paid` 等状态均表示 owner 明确确认的本地记录，不伪造外部投递、查看或到账证据。
- 不提供自动对账、税务申报、会计凭证、汇率同步、多币种折算或付款执行。
- 本地 Agent 或 AI 只能准备草稿、解释数据或生成待验收产物，不能确认付款、修改财务事实或对外发送。

## 当前实现状态

- `/income` 与 `/invoices` 路由、标题、空状态和外观按钮已经存在，但按钮没有业务行为，数据计数固定为零。
- 当前 schema v18 仍保留由迁移 001 创建的 `invoices` 表及客户、项目外键；v12–v18 的 Inbox、Reminder、编排、设置、保存视图与客户活动迁移均不改变发票结构。Client 基础 CRUD/人工活动与 Focus Core 已交付，但尚无发票 model、API、Query、CRUD、状态命令或 PDF 服务。
- 尚无 `financial_entries` 表，因此收入、支出、净现金流、KPI 和趋势统计均未实现。
- Sidecar 已注册任务、项目、客户、Actor 等基础 API，但没有财务或发票业务端点。
- 历史财务视觉原型已移除，后续以当前 React 实现、本文和 PRD 为准。

## 目标功能

### 收入与支出账本

- 新增、编辑、查看和删除收入/支出记录；删除前二次确认并保留审计事件。
- 按月份、类型、分类、客户、项目、发票和日期范围筛选。
- 区分已发生金额与待确认金额；支出由独立 `type` 表达，不以负数金额代替类型。
- 提供本地 CSV 导出；导出内容、范围和目标路径必须由用户确认。
- 计算本月收入、年度累计、平均客单价、收入、支出与净现金流；MRR 只有在经常性收入规则明确后才启用。

### 发票

- 创建、编辑、查看发票，并保证发票编号唯一；首版不新增 `archived` 业务状态。
- 从客户或项目预填必要信息，但保存前由 owner 核对金额、币种和日期。
- 支持 `draft → sent → viewed → paid`，以及到期未付款时进入 `overdue`；受控状态命令不得被普通 PATCH 绕过。
- 在本机生成 PDF 并保存到 `appDataDir/invoices/`；生成失败不得改变发票状态。
- 临近到期、到期和逾期只生成去重的本地 Inbox Item 或 Task，不自动催款。
- 标记已付款时，在同一幂等事务中创建或关联对应收入记录，避免重复入账。

## 关键用户流程

1. **记录收支**：用户选择收入或支出，填写整数金额、币种、日期、分类及可选关联，确认后写入账本并刷新统计。
2. **创建发票**：从发票页或已完成项目进入，选择客户和项目，核对编号、金额、开票日及到期日，保存为草稿。
3. **生成 PDF**：用户主动点击生成；Sidecar 在临时文件完成渲染与校验后原子移动到发票目录，再返回文件元数据。
4. **外部发送**：用户导出或打开 PDF 后自行发送；应用只允许用户手动把本地状态标记为已发送或已查看。
5. **到期跟踪**：本地调度器按用户时区扫描临期/逾期发票，以稳定事件键创建收件箱项；用户决定创建催款任务或忽略。
6. **确认付款**：owner 输入付款日期并确认；发票状态、唯一关联的收入记录和 Workflow Event 在一个事务内一致更新。随后通过任务命令完成/验收付款确认 Task，由 Inbox 服务按解决策略派生工作项状态，付款事务不直接关闭 Inbox Item。

## 数据、API、状态与事件

### 数据

- 复用并按递增迁移扩展 `invoices`：编号、客户、项目、`amount_minor`、币种、状态、开票/到期/付款日期、PDF 引用、备注、版本与审计时间。
- 新增 `financial_entries`：`type`、`amount_minor`、币种、发生日期、确认状态、分类、客户、项目、发票、备注、附件引用、版本及创建/更新时间。
- PDF 表内只保存受控相对引用、校验和与生成时间，不保存任意文件系统路径。
- 发票编号、付款入账关联和调度事件均需唯一约束或幂等键。

### API

- `GET / POST /api/v1/financial-entries`
- `GET / PATCH / DELETE /api/v1/financial-entries/:id`
- `GET / POST /api/v1/invoices`
- `GET / PATCH / DELETE /api/v1/invoices/:id`
- `POST /api/v1/invoices/:id/transition`
- `POST /api/v1/invoices/:id/generate-pdf`
- `GET /api/v1/stats/income`

列表接口支持分页、白名单排序和筛选；创建支持 `Idempotency-Key`，状态变化携带 `expected_version` 或 `If-Match`。

### 状态与事件

- 发票状态：`draft / sent / viewed / paid / overdue`；归档若未来需要，应使用独立展示字段并另行更新 PRD/迁移，不能私自增加业务状态。
- 财务记录确认状态：`pending / confirmed / voided`；冲正或作废保留历史，不静默覆盖原事实。
- 事件示例：`financial_entry.created`、`invoice.created`、`invoice.pdf_generated`、`invoice.status_changed`、`invoice.paid`、`invoice.overdue`。
- 每次状态变化追加 Workflow Event；调度生成 Inbox Item 时使用稳定 `source_event_key`，重扫不得重复创建。

## 与其他模块协作

- **客户**：发票必须关联客户；累计收入只从 `confirmed` Financial Entry 聚合，paid Invoice 只用于关联与对账，客户表不重复保存第二份总额。
- **项目**：项目可预填客户和金额；项目完成只提示生成发票，不自动创建或发送。
- **收件箱与任务**：临期、逾期、PDF 失败和待核对事项生成本地工作项；处理结果仍由财务事实决定。
- **自动化**：v0.2 规则只能创建本地提醒、Inbox Item 或 Task；v0.4 可消费财务事件，但不能对外发送或未经确认改变付款事实。
- **备份与恢复**：数据库、PDF、附件和 manifest 必须作为一致性备份集合验证。
- **AI/本地 Agent**：只能解释、分类或起草，不得执行付款确认、状态转换或外发。

## 分阶段实施

1. **F1 数据契约**：新增 `financial_entries` 迁移，明确发票状态机、金额/币种/日期约束、版本和事件格式。
2. **F2 账本闭环**：实现收支 CRUD、筛选、分页、删除确认、CSV 导出及定向测试。
3. **F3 发票闭环**：实现发票 CRUD、唯一编号、受控状态转换、客户/项目选择和详情页。
4. **F4 PDF**：实现本地模板、临时渲染、校验、原子落盘、重新生成和失败清理。
5. **F5 统计与协作**：实现真实聚合、付款原子入账、Inbox 事件及本地调度。
6. **F6 稳定性**：覆盖备份恢复、并发、低磁盘、损坏文件、跨时区和大数据量，并完成真实桌面验收。

## 验收标准

- 所有金额以整数存储和计算，格式化只发生在界面层；统计与明细可对账。
- 发票编号唯一，并发创建不会产生重复编号或部分记录。
- 非法状态跳转被拒绝；普通 PATCH 不能绕过付款确认等受控命令。
- PDF 生成失败、取消或低磁盘时不改变发票状态，不留下被数据库引用的残缺文件。
- 重复点击、网络重试和调度重扫不会重复创建发票、收入记录、事件或提醒。
- 标记付款后，发票、唯一财务记录和审计保持事务一致；相关 Inbox Item 只有在活动必需 Task 满足 resolution_policy 后才派生解决。
- 客户/项目删除约束可解释，历史发票和账本不丢失。
- 分页、筛选、空状态、加载、错误和重试均有前后端测试；统计在跨月和用户时区边界正确。
- 断网状态下 CRUD、PDF、统计、导出和提醒完整可用；不存在自动外发路径。
