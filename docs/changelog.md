# 变更记录

> 文档导航：[文档中心](README.md) · [产品需求文档](opc-workspace-PRD.md) · [整体功能架构](functional-architecture.md) · [模块文档](modules/README.md)

本文件是 opc-workspace 版本与实现切片的唯一变更记录。它承接原 PRD 附录 E「版本变更记录」，并合并了此前堆在 PRD、文档中心和模块索引顶部的切片说明。

- **按日期倒序排列**，同一天内较新的记录在前。带 `vX.Y` 的条目对应当时的 PRD 版本号；其余条目是没有单独升版的实现切片，编号形如 `H5-G51`、`H2-W13`、`AH-07`。
- **每条记录描述该切片交付当时的事实**，后续切片可能已经改变其中的行为、字段或版本号。判断“现在实现了什么”时以代码、测试和[模块文档](modules/README.md)为准，不以本文件为准。
- **同一切片只保留一条记录**。原先在多份文档中重复出现的说明已合并：“补充”是合并时保留的其他来源细节，“相关文档”是原说明指向的模块文档章节。
- **新增记录时在对应日期下追加一条**，不要再把切片说明写到 PRD、文档中心或模块索引的顶部。

## 2026-10-29

- 看板列内手动顺序拖拽（API v1 / schema 80，无迁移，只改前端）。看板此前只有跨列状态拖拽，列内顺序只能在列表视图"单一精确计划日期 + 手动顺序"下调整。现在工具栏排序选「手动顺序」时看板卡片可同列内拖拽排序：同列且同计划日期（含同为空）复用既有计划日期组"完整集合+版本"的原子 `POST /tasks/reorder`（服务端 `planned_date` 本就允许 null，未计划组可排），失败回弹并显示横幅；跨计划日期的列内拖拽不落库，横幅说明手动顺序按计划日期分组；其他排序下列内拖拽不启用，避免显示顺序不是手动顺序时"能拖但白拖"。同时移除两处冗余文字：列表状态组头的「本页 N」计数、日程视图顶部的"默认只包含活动任务"说明行。验证：TasksPage 新增 3 项测试（持久化、跨计划日期拒绝、非手动顺序不启用），`pnpm check:web` 全绿。相关文档：[任务管理](modules/tasks.md)。
- 任务页新增「按截止日」日程视图，并修正看板截止徽标差一天（API v1 / schema 80，无迁移，只改前端）。此前列表行只有项目、优先级和预计时长，截止时间要逐条打开详情才能看到；看板卡片的截止日期直接切分 ISO 字符串取 UTC 月/日，`2026-10-30T02:00+08:00` 会显示成 10/29。现在任务页分段控件增加第三种模式：前端用既有列表 API 一次读取当前筛选下带截止时间的任务全集（`due_from/due_to` 兜底为开区间，在 SQL 层排除无截止任务；状态留空等价 `active`；按 `due_date` 排序），客户端按本机自然日分组升序渲染为可折叠日期组，逾期各天与今天默认展开、逾期组头红字标注；组内行复用共享任务列表、勾选与批量操作，不提供拖拽排序（manual order 的语义属于状态+计划日期组）与分页；该模式不进保存视图，AI 交还返回统一落列表视图；列表/看板/按截止日的分段选择经本机浏览器存储 `opc-task-view-v1` 记忆，下次打开任务页恢复（AI 交还返回的显式视图优先），存储不可用时退内存、清除后回列表视图。看板截止徽标改用本机时区格式化（今天/明天、`MM/DD HH:mm`、跨年带年份），并按与服务端 24 小时 lead 同口径对逾期红、临期琥珀着色，终态不着色；格式化与判定抽为共享 `lib/taskDue.ts`。验证：taskDue 单测 11 项、agenda hook 分组测试、TasksPage 日程视图渲染与折叠测试、看板时区与着色测试，`pnpm check:web` 全绿。相关文档：[任务管理](modules/tasks.md)。
- 设置 → 外观新增字体大小（API v1 / schema 80，无迁移）。四档：小 90%、标准 100%、大 110%、特大 125%，点击即预览，保存后生效，取消恢复。`app_settings.appearance` 新增可选整数字段 `font_scale`（只接受 90/100/110/125，不可为 null），未写入过的行读取为 100，读取响应始终带该字段。界面样式使用固定像素，因此由桌面壳新增的 `set_interface_zoom` 命令（只接受上述四个百分比、经主 WebView 调用方校验）原生缩放可信主视图，文字与布局等比变化；内嵌浏览器子视图的摆放已按主视图缩放系数换算，页面本身不随之缩放。浏览器开发模式只保存偏好。旧版 Sidecar 严格拒绝未知字段，回退到本版本之前需使用升级前备份。
- 任务、项目界面精简与专注入口移除（API v1 / schema 80，无迁移，只改界面）。面向一人使用：新建任务与任务详情常驻名称、截止时间、项目、优先级、描述，计划日期、父任务、标签、完成标准、验收策略收进默认折叠的“更多选项”，任务类型与预计时长不再询问（新建固定 `work`、预计时长为空，已有任务保存时沿用原值）；任务详情的“责任分派”只在人工验收任务上出现，“产出与验收”只在人工验收或已有提交时出现，“Agent 执行”在本地 Agent 不可用且无 Run 时不显示（不再在每个任务顶部提示登记），“专注记录”移除，活动时间线收进折叠的“历史”。新建/编辑项目常驻名称、截止日期、描述，客户、合同金额、开始日期、颜色收进“更多选项”；项目详情去掉已记录工时、周期、任务类型筛选、项目专注区与“财务汇总尚未接入”提示，产出与附件合并进折叠的“文件”，活动时间线收进折叠的“历史”。专注的日常入口全部移除（左侧导航、工作台环形卡、右侧状态卡专注行、今日任务行“开始专注”、设置导航与命令面板的专注项），设置导航与命令面板也不再提供“人员与责任”；Focus API、`/focus` 路由、设置存储与已有数据保留，两个设置模块按模块 ID 仍可打开。
- 未开工作台权限时一次提出多个任务无法生成确认卡（API v1 / schema 80，无迁移）。旧式 `[opc:task]` 块在前端解析、服务端确认（`/ai/messages/:id/task-confirmation`）和 `ai_messages.task_id` 上都按“一条回复一个任务”设计，提示词却只写了“输出一个任务建议块”，没有说明多任务时怎么办；模型于是在一条回复里写出多个合规的块，前端整条判为“这条建议格式不完整”，用户反复要求也拿不到确认卡。现在提示词明确每条回复最多一个块，并让模型引导用户逐条确认，或在「工作台权限」里选择「准备操作建议」后由提案流程一次生成多张确认卡；前端遇到多个块时说明“每条回复只能确认一条，所以都没有创建”及这两种做法。旧式块一次确认多个任务需要调整 `ai_messages.task_id` 的一对一关系，未做。
- 修正 `GET /api/v1/agent-runs` 在没有匹配的 Run 时返回 `"data": null`（API v1 / schema 80，无迁移）。Go 的空切片经 `Scan` 后保持为 nil，序列化为 `null`；前端要求 `data` 为数组，于是把空结果当成格式无效，重试两次后在智能体侧栏的续办队列显示“续办队列读取不完整：无法读取独立执行”。没有任何需要处理的独立执行的工作区（`attention=1&plan_link=unplanned` 结果为空）每次都会遇到。现在列表固定返回 `[]`，新增空结果测试；对其余不带路径参数的 GET 接口在空工作区逐一核对，没有发现同类问题。

## 2026-10-17

- 已结束指派的导入（v0.3 高级导入，API v1 / schema 80，无迁移）。导入原先只对参与产出回放的 Task 在 Task 行之前写入已结束的指派，其余 Task 的已结束指派在 Task 之后按在线规则写入：已完成或已取消的任务被 schema 008 的终态守卫以 `TASK_NOT_ASSIGNABLE` 拒绝，已停用成员的历史指派被 schema 007 以 `ASSIGNMENT_ACTOR_NOT_ACTIVE` 拒绝，正常使用过的工作区因此几乎都无法导入。现在所有 `unassigned_at` 非空的指派都在 Task 之前写入，并临时启用其中已停用的 Actor；活动指派仍走在线规则，已结束的 Task 带活动指派的包在预检返回 422 `IMPORT_ROW_INVALID`。设置页 `TASK_NOT_ASSIGNABLE` 的说明改为只在追加导入、目标已有该已结束任务时出现的情形。修正了 ADR-034 已知限制中的对应条目。

## 2026-10-05

- 历史系统提醒的导入授权（[ADR-034](adr/034-inbox-source-import-authorizations.md)，v0.3 高级导入，API v1 / schema 79 → 80，迁移 080，非破坏性）。任务阻塞、任务到期、内容日历与路线图里程碑四种系统提醒的插入守卫只接受“来源此刻仍处于被投影状态且未删除”的行，而导入按最终状态写入：来源之后解除阻塞、完成、改期、改名或被删除的提醒让整个包无法导入。迁移 080 新增操作态表 `business_import_inbox_source_authorizations` 并重建四个守卫：导入先核对包内的投影事件与删除事件，再为每条提醒写一次性授权，守卫放行被授权且来源存在（或记录为已删除且确实不存在）的行；没有授权的在线投影规则不变，形状检查改为对缺失字段也成立。schema 79 成为受支持的旧源（49、51、63–79），其排除表清单被冻结；可导出结构不变，没有新的转换步骤。同时修正 schema 050 的包内校验：项目删除后被重新打开的完成提醒不再被判为无效。设置页去掉“历史提醒目前还不能导入”的说明，新增“来源已删除但目标仍持有”与“历史指派尚不支持”的说明。验证中另发现一条既有规则仍然阻止导入：已完成或已取消、并且指派过负责人的 Task，其已结束的指派行会被 schema 008 的终态任务守卫拒绝（`TASK_NOT_ASSIGNABLE`，演练在备份前拒绝）；本切片没有修复，已记入 ADR-034 已知限制。

## 2026-10-04

- 业务导入的应用前演练（[ADR-032](adr/032-business-import-upgrade-and-conflict-strategies.md) S5，v0.3 高级导入，API v1 / schema 79，无迁移）。此前预检只凭包和目标的键来预测结果，数据库自身的规则（触发器、约束）要到真正写入时才遇到，那时回滚备份已经创建，失败的导入每试一次就留下一个备份。现在预检得出“可以应用”之后，把同一份方案在一个始终回滚的事务里完整写入一遍；会被拒绝的导入返回阻断原因 `apply_rehearsal_failed` 与那条规则的标识，应用请求返回 422 `IMPORT_REHEARSAL_FAILED`，不创建备份、不发布文件。设置页说明原因并给出规则代码，确认按钮不可用。同时更正一处文档口径：原先记为“到期提醒历史无法导入”的缺陷，实测范围更大——任务到期与任务阻塞的历史提醒都已用真实导出复现，内容日历与路线图里程碑的守卫逻辑相同。这些包现在在预检阶段被明确拒绝，但仍然导不进来；放行需要把 schema 050 的导入授权表推广到这四种来源，是另一项需要迁移的工作，尚未立项。三个旧测试原先断言“备份之后失败并回滚”，已改为断言“备份之前被拒”；文件发布后的补偿路径改用“受控存储里有多余文件”来覆盖。
- 执行抽屉与任务详情的层叠顺序（无 API 或 schema 变化）。指向某次执行的链接会同时打开执行抽屉和任务详情，任务详情加载较晚，于是压在抽屉上面，抽屉要等它关掉才能操作；ADR-033 的第二次确认恰好在抽屉里。现在浮层栈支持“在指定浮层下方打开”，同一任务的详情在抽屉已打开时排到其下方，并且浮层按栈顺序绘制而不再依赖 DOM 顺序。其余浮层的行为不变。
- Agent 计划：前置步骤的文件产出作为后续步骤的输入（[ADR-033](adr/033-agent-run-predecessor-file-inputs.md)，T-19 v0.2 受控切片，API v1 / schema 79，无迁移）。此前延后启动只表达顺序，后续 Run 的输入在确认时冻结，那时前置产出还不存在。现在 AI `agent_run.start` 可在门控之外声明 `start_after_input=predecessor_files`：仅限 `accepted` 条件、两个任务同属一个项目、前置 Run 约定产出文件，且只传一步。采用两段人工确认：第一段在确认卡上确认这个安排（新增独立同意 `confirm_agent_predecessor_input`），Run 以执行契约 v7 入队，快照只冻结“将使用哪些文件”的声明；第二段在前置产出被验收后，由人在该 Run 的执行抽屉里逐份核对文件名、大小、SHA-256、来源批次与接收的 Provider 并确认，这次确认记录为门控的放行事件（含文件引用、Provider 身份与确认人，不含正文和路径）。对账器对这类门控从不自动放行；验收后产出不可用（任务被重新打开、文件被删除、任务移出项目）时以新原因 `predecessor_output_unavailable` 取消。新增原生端点 `GET /api/v1/agent-runs/:id/start-gate/inputs` 与 `POST …/inputs/confirm`，模型工具不可达。认领与启动前再次核对文件字节，不一致即失败关闭；已绑定文件受删除互锁保护；v7 Run 不能原样重试，界面不再为它显示「重试」。同时修正一处既有缺口：任务的 Run 列表与 Run 详情此前没有写出已计算的 `start_gate`，执行抽屉的「启动条件」因此没有数据；这一栏真正显示后改为整行展示完整的条件、截止时间与前置执行 ID。取消等待中的执行后、对账器关闭门控之前的瞬时响应（已取消而门控仍在等待）此前会被前端当作无效响应，现在按对账规则读作以 `run_not_queued` 关闭。`external` Runner 保持关闭。已知限制：统一 Agent Inbox 没有“待确认输入文件”的专门条目；不传递文本产出、不跨项目、不链式传递。真机验收清单新增 A9，现共 44 项，全部待验收；真实 Provider 下的整条链路没有执行过。
